## Сокращённый гайд

**Команда для запуска скрипта установки (скопировать и запустить НА СЕРВЕРЕ):**
```bash
curl -O https://raw.githubusercontent.com/kryptonmourog/matrix-instruction-and-configs/refs/tags/v1.3.0/scripts/matrix_up.sh && chmod +x matrix_up.sh && sudo ./matrix_up.sh
```

В терминале скрипт показывает интерфейс на [gum](https://github.com/charmbracelet/gum): вопросы по одному с подсказками по умолчанию (поддомены предлагаются от основного домена), **Esc — вернуться к предыдущему вопросу**, в конце — экран проверки, где любое значение можно исправить. Установка идёт по шагам со спиннером, а подробный вывод пишется в `/var/log/matrix_up.log`; при ошибке скрипт показывает последние строки журнала. gum скачивается один раз (версия и контрольная сумма зафиксированы) в `/usr/local/lib/matrix_up/` и используется при следующих запусках; в `PATH` он не добавляется. Без терминала, при недоступности gum или с флагом `--plain` скрипт работает в обычном текстовом режиме; там вернуться назад можно, ответив `<`. Если ответы подаются не с клавиатуры (из файла или другой программы), экран проверки не показывается, а таблица параметров просто выводится.

После первого запуска скрипт копирует себя в систему, и дальше он доступен как команда **`sudo matrix-up`** (или `matrix_up`). На сервере с установленным Matrix команда открывает панель управления: состояние сервисов, обновление, установка и удаление админок и моста Telegram, изменение параметров с переустановкой, журнал установки. Без установленного Matrix команда запускает установку.

**Админки.** Можно поставить обе одновременно, при установке скрипт спрашивает про каждую:
- **Ketesa** (бывший synapse-admin) — полнофункциональная: пользователи, комнаты, медиа, сессии, MAS. Открывается на домене Matrix по адресу `https://<домен Matrix>/synapse-admin/`, отдельный домен не нужен.
- **Element Admin** — проще, на отдельном поддомене.

Потом любую из них можно установить или удалить в панели `sudo matrix-up`: скрипт меняет одну строку в `vars.yml` (с бэкапом) и применяет плейбук.

**Мост Telegram** ([telegram-bridge-advanced](https://github.com/kryptonmourog/telegram-bridge-advanced) — форк mautrix-telegram: папки как пространства, комментарии, опросы и другое). Установщик спрашивает, ставить ли его и где:
- **На этом сервере** — встроенной ролью плейбука с образом форка. Telegram должен открываться с сервера; если стоит Xray, мост ходит в Telegram через него (SOCKS5).
- **На отдельном сервере** — зарубежный VPS, если Telegram с сервера Matrix недоступен. Мост ставит роль [telegram-bridge-advanced-ansible](https://github.com/kryptonmourog/telegram-bridge-advanced-ansible) (кладётся в каталог плейбука как `telegram-advanced`), мост сам подключается к серверу Matrix через wsproxy, новых портов не нужно. Скрипт заходит на VPS по SSH под root своим ключом `/root/.ssh/matrix_up_telegram`: открытый ключ он покажет, добавить его можно вручную или вводом пароля root от VPS. По желанию — прямые медиа (отдельный поддомен на сервер Matrix).

Следующие вопросы зависят от выбора: `api_id` и `api_hash` с [my.telegram.org](https://my.telegram.org/apps), шифрование личных чатов, для отдельного сервера — его адрес, SSH-порт и прямые медиа. Настройки моста пишутся в `vars.yml` отдельным блоком (`# >>> matrix-up: мост Telegram`). После установки напишите `login qr` боту `@telegrambot:<домен>`.

В панели `sudo matrix-up` мост можно установить на уже работающий сервер (в том числе поставленный прошлыми версиями скрипта), удалить (и встроенный mautrix-telegram, оригинальный или форк, и мост на отдельном сервере; комнаты в Matrix остаются, базу моста можно оставить), перевести оригинальный mautrix-telegram на форк с сохранением базы и входа, а мост, поставленный на отдельный сервер вручную (wsproxy на сервере Matrix), подключить к скрипту. `--update` обновляет и мост на отдельном сервере.

Если мост с шифрованием возвращают на сервер, где у бота остались ключи подписи от другой базы, локальная установка автоматически заменяет недоступный старый ключ. Для моста на отдельном сервере роль не может обнаружить это до первого запуска. Если такой мост падает с `Failed to verify with recovery key`, замените в его базе значение `recovery_key` на `overwrite` и перезапустите мост.

Ответы и сгенерированные секреты сохраняются в `/etc/matrix_up/matrix.env`, поэтому повторная установка спрашивает только логин и пароль админа, а пароль базы и ключи не меняет. Файл `.env`, который прошлые версии клали рядом со скриптом, переносится туда автоматически. Если на сервере уже есть установка (в том числе сделанная прошлыми версиями скрипта), её домены и секреты тоже переносятся автоматически.

**Обновление уже установленного сервера** (в том числе поставленного прошлыми версиями скрипта):
```bash
sudo matrix-up --update
```
Если команды `matrix-up` ещё нет (сервер ставился версией до v1.2.0):
```bash
curl -O https://raw.githubusercontent.com/kryptonmourog/matrix-instruction-and-configs/refs/tags/v1.3.0/scripts/matrix_up.sh && chmod +x matrix_up.sh && sudo ./matrix_up.sh --update
```
Та же команда без `--update` открывает панель — так можно поставить мост Telegram на сервер, установленный прошлыми версиями скрипта.

Сначала `--update` проверяет, не вышел ли более новый релиз скрипта той же мажорной версии (v1.x), и если вышел, скачивает его, проверяет и продолжает уже новой версией. На следующую мажорную версию (v2.0.0) скрипт сам не переходит, только предупреждает. Остаться на текущей версии: `sudo matrix-up --update --no-self-update`.

Режим `--update` ничего не спрашивает и не пересоздаёт `vars.yml`, поэтому ручные правки в нём сохраняются. Он переводит плейбук на версию, проверенную в этом релизе (более новую не откатывает), обновляет роли и запускает установку. В `vars.yml` меняется только `matrix_playbook_migration_validated_version`, прошлый файл сохраняется рядом как `vars.yml.bak-ДАТА`.
